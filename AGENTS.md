# BrightFox: handbook for coding agents (Codex, Claude Code) and developers

BrightFox (https://brightfox.si) is a family study app for kids at a Slovenian school. It has three parts:

- **Topics**, each one a path: 📖 *Uči se* (notes, flashcards, an "I can" list) → ✏️ *Vaja* (practice) →
  🏆 *Liga prvakov* (a harder level that wins a trophy).
- **Tests**: readiness, a daily plan, knowledge gaps, *Moje napake* (spaced review of mistakes), mock tests
  and a typed oral exam.
- **Foxy**, a homework tutor on the Claude API that gives hints before answers.

Parents (admins) see everything in their own family and approve content. Kids (learners) see only their
own space. It is built for many families from day one, so it can be sold later.

> The code name is **`ucilnica`**: the folder, the `/opt/ucilnica` server path, the `UCILNICA_*` env vars, the
> Docker service, the `uc_session` cookie. Users never see it; leave it as it is. `CLAUDE.md` holds the
> same rules in short form for Claude Code.

## 1. Hard rules (read before changing anything)

1. **Families never see each other.**
   - Every learner-owned table has `family_id`, and a two-column foreign key `(family_id, learner_id)` →
     `learners(family_id, id)`.
   - Every `/api` route depends on **exactly one** access dependency from `backend/app/access.py`:
     `public`, `self_ctx`, `admin_ctx` or `learner_in_scope`.
   - `backend/tests/test_tenancy.py` audits every route and probes other families' ids, which must answer
     404. New routes are covered automatically; keep that test green.
2. **Kid-facing Slovene is gender-neutral toward the child.**
   - Use imperatives and the present tense ("Izračunaj", "Zapiši").
   - Never l-participles or adjectives about "you" ("Si naredil?", "pripravljen").
   - The content checker refuses common gendered forms.
   - Foxy himself is **masculine**: "Vprašaj Foxyja", "s Foxyjem", "Foxy je pripravljen".
3. **No streaks**, nothing that punishes a missed day. Readiness % and mastery are fine; trophies are
   collected and never lost.
4. **Tests use scratch data only.**
   - `backend/tests/conftest.py` points `UCILNICA_DATA_DIR` at a temp folder and makes scratch families.
   - Never use real logins or the real `data/` folder.
5. **The AI is never called from tests.** Use `llm_service.set_test_provider(fake)`.
   `backend/evals/run_eval.py` does call the real API and costs money: ask the parent first, quote the
   estimate (`--dry-run`), and always pass `--max-usd`.
6. **Never type or store passwords or API keys** for anyone.
   - Logins are set by the person, in a hidden prompt or in the app.
   - The API key goes in with `deploy\set-anthropic-key.ps1`, which uses a hidden prompt on the server.
7. **Database migrations only add things** (new tables or columns) once something is in production.
   - Never let Alembic batch-recreate a table that others reference: SQLite with `foreign_keys=ON`
     cascade-deletes the child rows.
   - Check every autogenerated migration by hand.
8. **Every content change raises `version`.** The parent then approves the topic or mock again.

## 3. How the main features work

### Topics and approvals
- Topics and mocks are **JSON files**, checked by `backend/app/content/checker.py`. The format is in
  `docs/content-format.md`.
- A topic is visible to a learner only when `content_access` has a row for that learner **at the file's
  current version**. A changed file disappears from the kid's view until a parent approves it again.
- `content/data/global/` is offered to every family. `content/data/families/<slug>/` is that family's alone.
  The real family's slug is `danijel`.

### Writing a topic from homework photos
Today a coding agent writes topics; there is no in-app generation. The agent:
1. Reads the photos.
2. Works out the topic, the grade and the school's method (Slovenian notation: decimal comma, `·`, `:`).
3. Writes a **new** topic JSON. It never copies the book: the numbers, stories and wording change, and the
   topic starts easier than the book.
   - `study`: sections with tables, examples and "Pazi!" mistakes; flashcards; "I can" goals with ids.
   - `skills`.
   - `tasks`: warm-up → practice → challenge, 1–2 hints each, a worked solution, `traps` built from the
     kid's typed mistakes.
   - `challenge`: the Liga prvakov level.
   - `parent`: the parent helper card.
   - `oral`: oral-exam questions.
   - optionally a **mock** in `.../mocks/`.
4. Runs `backend\.venv\Scripts\python.exe -m app.content.checker` and the tests, then deploys.

The parent approves it in the app.

### Practice data and progress
- A run is one `practice_runs` row with one `task_results` row per task: right first time, tries, hints,
  solution shown, typed mistakes.
- Mastery, readiness, the plan, gaps and Moje napake are **pure functions** in `backend/app/learning/`,
  computed on request and never stored. `docs/readiness.md` explains them for parents.

### Foxy (the AI tutor)
- `routers/tutor.py` builds the request:
  - the system blocks: Foxy's rules (cached), the topic block when the chat started from a topic (cached),
    and the learner context;
  - the chat history: text only, no thinking blocks.
- It calls `llm/service.complete`, then writes the reply and a row in the `llm_calls` cost ledger.
- Database reads happen before the AI call and writes after it, so no transaction waits on the network.
- **Limits:** a daily limit per learner (the oral exam counts too), plus an optional monthly family budget.
- **Model per job** (`tutor_chat`, `oral_grading`, `open_feedback`):
  - The default is Claude Opus 5.5 at medium effort.
  - A family can only pick models listed in `llm/approved_models.json`, and a model is listed only after
    it passed `backend/evals`.
  - Haiku 5.5 has **no** server-side fallback; Opus and Sonnet 5.5 use `fallbacks: "default"`.

## 4. Commands (Windows, from the project folder)

> **Python on Windows:** never run bare `python` or `py` on these PCs: they can be the Microsoft Store alias,
> which hangs. Always use `backend\.venv\Scripts\python.exe`. First setup: `setup.bat`. It finds Python
> 3.12 in `%LOCALAPPDATA%\Programs\Python\Python312`, makes the venv and installs both halves.
>
> **Smart App Control** (Windows) blocks SQLAlchemy's freshly installed compiled files. `setup.bat` deletes
> them, and SQLAlchemy then runs in pure Python. Never switch Smart App Control off.

| What | Command |
|---|---|
| Run locally | `start.bat` (web http://localhost:7686, API 7687); `stop.bat` |
| Backend tests | `cd backend` then `.venv\Scripts\python.exe -m pytest -q` |
| Check content | `cd backend` then `.venv\Scripts\python.exe -m app.content.checker` |
| Frontend typecheck + tests | `cd frontend` then `npx tsc -b` and `npx vitest run` |
| New migration | `cd backend`, set `$env:UCILNICA_DATA_DIR` to a scratch folder, `.venv\Scripts\python.exe -m alembic upgrade head`, then `... -m alembic revision --autogenerate --rev-id 0004 -m "<what>"`; **read the file** (only create/add) |
| Local accounts | `.venv\Scripts\python.exe -m app.manage create-family <slug> --name "<name>"`, `add-learner`, `set-password <user> --family <slug> [--learner <name>]` |

**Before calling anything done:**
- backend pytest, `npx tsc -b` and `npx vitest run` all pass;
- the content checker passes if content changed;
- for UI changes, try it on a scratch server with scratch accounts.

## 5. Deploying (see `deploy/DEPLOYMENT.md`)

- `powershell -ExecutionPolicy Bypass -File deploy\deploy.ps1` packs the code (never `data`, `.venv` or
  `node_modules`) and uploads it to `footballadmin@152.53.191.32:/opt/ucilnica`. The server then makes a
  backup, builds the Docker image, waits for the health check, and **rolls back by itself** if it fails.
- Afterwards: `powershell -ExecutionPolicy Bypass -File deploy\smoke-test.ps1`. It is read-only, uses only
  the QA family's logins from `Documents\Ucilnica-qa-login.txt`, and must end with 0 failed.
- It needs an SSH key that the server accepts, unlocked with `ssh-add`. `deploy.ps1` uses
  `%USERPROFILE%\.ssh\football7676_final` by default. On another PC, use that PC's own key; the server owner
  adds its public key to `~/.ssh/authorized_keys`.
- The Caddy site block for brightfox.si lives in **PitchDriven's** `deploy/Caddyfile` (one Caddy serves all
  sites). Change it only together with PitchDriven's deploy.
- **More than one PC works on this code.** `deploy.ps1` uploads the local folder and replaces what is on the
  server, so deploy only right after `git pull`, with everything committed and pushed. See
  `docs/new-pc-setup.md`.
- Photos that topics are made from stay outside the repository. Textbook pages and the kids' work never go on
  GitHub.

## 6. Gotchas learned the hard way

- **PowerShell → ssh:** send multi-line remote commands as an LF-only script file
  (`cmd /c "ssh host bash -s < file.sh"`). Give `docker compose exec -T` a `</dev/null`, or it swallows the
  rest of the script.
- **PowerShell arrays:** `@(@("a","b"))` flattens to `@("a","b")`, so a one-pair replacement table iterates
  characters. Prefer the editor (or Python) for text replacements.
- **Times and dates:** each family has a time zone. The browser's "today" is trusted only within ±1 day of
  the server's date.
- **The browser runs the answer checking** (`features/learning/answers.ts`) for practice and mocks. The server
  stores what it is told; fine for a family app.
- **Photos** are saved under `data/files/<family>/<learner>/`, are never public, and are included in every
  backup.
